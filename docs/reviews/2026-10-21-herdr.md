# Herdr review — 2026-10-21

Reviewed `feature/sh-herdr` at `68436a82a442f2febfcaa674825cb33590234718`,
including lifecycle templates, attachment, setup, state handling, tests, and
documented behavior. Herdr implementation was not changed.

**Assessment:** the normal path has substantial test coverage, but the app
should not be treated as fully verified until the isolation and attachment
issues below are addressed and a live allocation is exercised.

## Findings

### P1 — Two jobs can reclaim the same stale session lock

`sh_herdr/lib/runtime.sh:124–127`: both callers can read the expired owner before
either updates the lock. After the first caller acquires the session, the
second caller renames and removes that **new active lock**, based on its old
owner snapshot. Both calls return success and can start servers writing the
same durable Herdr session. Existing tests cover only sequential reclamation.

A deterministic local reproduction made both jobs 200 and 300 active in the
fake scheduler while expiring original owner 100. Its result was:

```text
A acquire status=0, owner=200
B acquire status=0, owner=300
Final owner=300 (both jobs active throughout)
```

Serialize all acquisition, reclamation, and release operations with a lock
whose semantics are valid on Sherlock's shared filesystem. Merely checking
the owner again before `mv` leaves another check/use race.

### P2 — Names longer than Herdr supports lose session isolation

`sh_herdr/lib/runtime.sh:7–10`: the app accepts arbitrarily long session names.
Herdr's limit is 64 bytes. With an explicit `HERDR_SOCKET_PATH`, Herdr filters
an invalid environment name and silently uses default durable storage.
Separate long names therefore have different app locks and sockets but share
Herdr's default state.

A 65-character ASCII name passed the app validator while actual Herdr 0.8.2
returned `"session":null` from `status server --json` against an absent
isolated socket. The [0.9.5 session implementation](https://github.com/herdrdev/herdr/blob/v0.9.5/src/session.rs)
retains the limit. Reject names exceeding 64 bytes before creating state.

### P2 — Attach may start a replacement server

`sh_herdr/bin/sherlock-herdr-attach:66–67`: bare `herdr` starts a server when
the socket is absent. The app publishes its registry before readiness, and
its server-health loop checks every five seconds. An early attach or an
attach immediately after server failure can thus create a replacement
daemon from the attachment environment, without the batch job's module and
initialization settings.

Use client-only attachment: `herdr client`. The actual 0.8.2 binary accepts
that command and exits with `failed to connect to server` on an absent
socket without starting a daemon. The relevant upstream paths are
[`main.rs`](https://github.com/herdrdev/herdr/blob/v0.8.2/src/main.rs) and
[`server/autodetect.rs`](https://github.com/herdrdev/herdr/blob/v0.8.2/src/server/autodetect.rs).
Slurm cleanup of an inadvertently started daemon was not tested live.

### P2 — Custom install root is not passed to the real installer

`sh_herdr/bin/setup:27`: fresh installation exports
`SHERLOCK_HERDR_INSTALL_ROOT`, but the [real installer](https://herdr.dev/install.sh)
reads `HERDR_INSTALL_DIR`. A non-default installation root therefore installs
to `~/.local/bin` and fails the wrapper's expected-path check. Pass
`HERDR_INSTALL_DIR="$install_root/bin"`. The fake installer in the tests
consumes the app-specific variable, masking the mismatch. Default-path setup
is unaffected.

### P3 — Runtime tests hardcode UID 501

`sh_herdr/test/test_runtime.bash:44–51,80,85`: socket fixtures embed UID 501,
while production validates the real `$UID`. The suite consequently fails on
other accounts, including Sherlock users. Use the current UID in independent
fixture expectations.

## Evidence and limits

- `bash sh_herdr/test/run`: passed on the local UID-501 account, including
  Ruby **9 runs / 120 assertions** and the Bash runtime, helper, setup, and
  lifecycle suites. ShellCheck was not installed and was explicitly skipped.
- A separate reviewer inspected the code and upstream behavior; the parent
  independently reproduced the stale-lock race.
- Read-only Sherlock inspection confirmed deployed checkout commit
  `68436a8`, Herdr **0.8.2**, and current **v8 Claude and Codex integrations**.
  `module reset; module load system git; module load claude-code codex`
  succeeded for this account.
- No live Herdr startup, attach/detach, concurrent allocation, cancellation,
  or cross-allocation restore test was performed. Passing mocked lifecycle
  tests does not establish those live behaviors.

Recommended acceptance after fixes: start a named session, launch each agent,
detach and reattach, reject a duplicate active name, cancel, reuse the name,
and confirm the documented restoration behavior. Test concurrent stale-owner
reclamation before relying on shared named sessions.
